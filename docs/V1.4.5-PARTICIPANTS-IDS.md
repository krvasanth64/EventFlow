# EventFlow V1.4.5 Beta — Permanent Event Codes and Participant Preparation

## Immutable event-scoped identifiers

- Each event assigns P0001, P0002, ... to Programs and A0001, A0002, ... to Awards.
- Codes are **unique within the event**, not globally across different events. For example, Event X P0001 and Event Y P0001 are both valid.
- The code stays on the same record regardless of drag/drop, status, completion, cancellation, media changes or edits.
- Deleted display codes are never reused within the same event. Capacity is 9,999 codes per record type and event.
- Internal UUID values remain unchanged and are used for linked API operations.
- Existing programs and awards receive deterministic code assignments on first V1.4.5 server startup, sorted by current order, without changing their internal UUIDs. A database snapshot **before** first update is recommended.
- The code is shown in Program Planner, Live running order, Award Planner, Live Award list, DJ export manifest, DJ ZIP media filenames, URL exports and print layouts.

## Program participants

Each Program contains a participant child table with:

| Field | Description |
|---|---|
| Participant row ID | Stable internal UUID |
| Employee code | Optional staff/participant code; duplicate codes within the same program are blocked |
| Participant name | Required |
| Contact | Optional mobile/contact value |
| Ready / Checked In | Toggle by Admin, Editor or Live Controller |
| Checked At | Timestamp when marked ready |
| Checked By | Username who checked the participant |

Editor/Admin with event edit lease can manage the roster. The former single employee name/code/contact fields are hidden from the current edit UI and migrated into the first participant row for historical entries, preserving their values.

The operator uses a **Participants · Next 4** navigation page. It lists the first four Pending / Ready / Stopped programs in the current running order, with every participant and a readiness summary. The same view is shown under Live Control. Skipped and completed programs are excluded from the Next 4 list; the active program is not reordered or reset when participants are checked. Changes broadcast to other authenticated browsers via existing real-time event revision messages.

**Role permissions:** Admin/Editor can edit roster after taking the editor lease. Admin/Editor/Live Controller can check or uncheck roster readiness. Viewer has read-only access.

## QA steps

1. Back up `D:\EventFlow-V14-Data`, stop test server.
2. Pull the feature branch, run `node --check server.js`, `node --check public/v16.js`, `npm test`.
3. Start with the **same** `EVENTFLOW_DATA` to migrate historical records once.
4. Open an existing event and confirm each program has P#### and each award A####. Drag items; codes must remain unchanged.
5. Edit a program and use **Manage participants** to add multiple people. Save roster; verify it remains attached to the correct Program ID.
6. Open **Participants · Next 4**. Verify order and each row. Check one participant as a Live Controller; verify the green ready state and timestamp remains after refresh.
7. Open Live Control on another browser. Confirm the next four readiness cards and current on-air program remain unchanged.
8. Finish a program; the Next 4 list should advance. Skip/restore; list should reflect the running order.
9. Download DJ Package ZIP, inspect `DJ_MANIFEST.json` and `DJ_RUNNING_ORDER.csv`; code must remain stable after reorder.
10. Try a Viewer check-in action; server must deny it.

# EventFlow V1.5.0-beta — Coolify staging deployment runbook

> **Staging only.** Live Internet production deployment has not been approved. Use a separate subdomain and a dedicated empty persistent volume. Do not connect staging to the existing Windows event data directory.

## Current engineering baseline

- Source repository: `krvasanth64/EventFlow`
- Branch: `feature/live-console-v14-foundation`, Pull Request #1 stays draft
- Docker image: `node:22-alpine` using `npm ci --omit=dev` against committed `package-lock.json`
- Runtime: independent Node.js service; **one instance only** because sessions/edit leases are in memory and the JSON database has no cross-replica locking
- Internal HTTP port: `8765`
- Persistent runtime directory: `/data` (events JSON, media uploads, backups)
- App user UID/GID: `10001`
- Initial admin bootstrapping: **only on an empty runtime**, with a one-time strong password securely configured in Coolify

## Coolify setup

1. Prepare a connected Coolify server with Docker, working proxy and reachable HTTPS domain. Example only: `https://eventflow-staging.example.com`.
2. In Coolify, open **Project → staging environment → New Resource → Application**. Select the GitHub repository `krvasanth64/EventFlow` and **feature/live-console-v14-foundation** branch.
3. Select **Dockerfile** build pack and `./Dockerfile` path. Do **not** select Nixpacks, Node static hosting, or a generic Node start command.
4. In **General**, set the application internal/exposed port to `8765`; configure the domain through **Domains** with HTTPS. Avoid publishing a direct host port mapping.
5. **Before the first deployment**, go to **Configuration → Persistent Storage → Add → Volume Mount**. Create a dedicated named volume such as `eventflow-staging-data` with **Destination Path** `/data`. No other application or preview must share this volume.
6. In **Environment Variables**, set:

```dotenv
NODE_ENV=production
HOST=0.0.0.0
PORT=8765
EVENTFLOW_DATA=/data
EVENTFLOW_SECURE_COOKIES=1
EVENTFLOW_PUBLIC_ORIGIN=https://eventflow-staging.example.com
```

Set `EVENTFLOW_PUBLIC_ORIGIN` to the **real exact browser HTTPS origin**, including scheme and any nonstandard port, with no path or trailing slash.

7. Only for **initial bootstrap**, add `EVENTFLOW_ADMIN_PASSWORD` as a secret value. Use a unique strong password that is not copied into GitHub or chat. Deploy, sign in as `admin`, confirm persistence, then remove the bootstrap variable and redeploy. Login sessions will reset after restarting the Node process.
8. Keep **auto-deploy disabled** during the pilot. Use a single replica and do not enable parallel rollouts.
9. Keep staging accessible to trusted testers only (VPN/private ingress or reverse-proxy allowlist). The current `npm audit` reports two moderate findings, and the app has not completed a full public-exposure security review.

## Acceptance test after first deploy

- [ ] Coolify Deployment Logs report successful build and healthy running container.
- [ ] `https://<staging-domain>/api/health` returns `ok:true` and `version:1.5.0-beta`.
- [ ] Admin login/logout works with Secure cookies; a cross-origin POST is rejected when `EVENTFLOW_PUBLIC_ORIGIN` is configured.
- [ ] Create a **synthetic demo event** from frontend; original media uploads persist.
- [ ] Program and Award PDF previews/downloads contain no extra footer-only pages.
- [ ] LED Timeline shows **only current live + next four** programs; no completed column.
- [ ] Award recipients check in from Backstage; awards appear on LED only when every recipient has checked in; presented/skipped awards disappear from ready feed.
- [ ] At least two browsers (DJ operator + remote LED display) receive live status via SSE; note media playback runs on the DJ computer, not synchronized as streamed audio to the LED.
- [ ] Stop/restart container; events, users, readiness and uploaded media remain available in the exact same `/data` volume.
- [ ] Download full backup ZIP; verify integrity and restore into an **independent** recovery volume or Windows test folder.
- [ ] Confirm DNS/TLS renewal and test mobile navigation.

## What the automated Docker test proves

GitHub Actions builds the same Dockerfile, starts a temporary container with one-time initial admin secret, checks `/api/health`, then restarts a second container attached to the same dedicated named volume **without the bootstrap secret** and confirms the previous user persists.

This test is **not** a substitute for Coolify server, domain, proxy, TLS, backup or real-device testing.

## Hold conditions for public production

- Two moderate npm security warnings remain unresolved in the ExcelJS/uuid dependency chain.
- Sessions and edit leases are process-memory only. Concurrent replicas are unsafe.
- Production login rate limiting, abuse prevention, exhaustive CSRF/authentication controls and reverse-proxy security policies remain unverified.
- Full event-day media playback, restoration and backup runbook on the actual server require acceptance.
- Do not merge PR #1 to `main` or point the production hostname at this staging service before approval.

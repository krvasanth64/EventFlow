# EventFlow V1.5.2-beta — Fast sign-in, scoped live collaboration, admin event lifecycle

## Code and deployment

Feature branch: `feature/live-console-v14-foundation`. Main remains unchanged. No SQLite conversion is included.

## 1. Login and per-event focus

- As soon as credentials authenticate, show **Choose an event**. Only the lightweight active event list loads.
- No complete program, award, participant, media or event history is downloaded until the user selects the event.
- The selected event remains active across the planner, Backstage, Live Control, Awards, Reports and LED pages. SSE ignores updates for other events.
- Login password verification uses asynchronous scrypt to avoid pausing the live event server during concurrent logins.
- The event list response excludes heavy catalog details. Selecting an event fetches fresh authenticated data on demand.

## 2. Independent sessions and automatic logout mitigation

- Login sessions are now stored in `EVENTFLOW_DATA/sessions.json` as SHA-256 hashes of random session identifiers, with user IDs and expirations; raw bearer cookie tokens are **not** written to disk.
- An application restart no longer invalidates all users' active sessions. Valid sessions still have a 12-hour maximum from login; explicit logout and disabled accounts still revoke access.
- Different devices or separate browser profiles have independent sessions. Two accounts in tabs of the same browser profile cannot remain independently logged in to the same origin because tabs share cookies.
- The browser does not log out an already loaded valid session on a temporary network failure; it reconnects.
- `sessions.json` is private state and must not be committed to Git or shared. A complete recovery that replaces the entire runtime may still require users to log in again.

## 3. Live collaboration

- SSE events include the audit actor so clients can identify other operators' changes.
- Live Control shows a brief informational warning when another account modifies the **selected event** in a way relevant to live operation.
- Other events and unrelated screens synchronize without disruptive Live Control warnings.
- Existing event revisions, editing leases, and operation permission checks remain in place; simultaneous action conflicts continue to return 409.
- Only the active event is loaded, avoiding unnecessary public internet traffic.

## 4. Admin Event Management

A new admin-only **Event Management** page lists all active and archived events with Program/Award counts.

- **Archive / Inactive**: hides an event from users' normal event lists and prevents further operational changes; does not delete any data or uploaded media.
- **Restore**: returns the event to the normal event list. The original status, IDs, order, media and readiness remain.
- **Permanently delete**: administrator-only; requires event to be archived and not live, no active editing lease, two confirmations and typing the exact event title. Removes event, program and award records and the event's media directory.
- A deletion audit entry and private JSON snapshot are retained in the backups directory. **That snapshot does not contain media.** Download and verify a complete ZIP backup before deleting a real event.
- The old generic DELETE event route is blocked; it cannot bypass admin workflow.

## 5. Recommended Windows test sequence

When no live event is running, stop the sole EventFlow Node process. Verify the backup before deployment.

```powershell
cd D:\EventFlow-V14-Test
$backup = "D:\EventFlow-V14-Backup-" + (Get-Date -Format "yyyyMMdd-HHmmss")
Copy-Item "D:\EventFlow-V14-Data" $backup -Recurse
git pull --ff-only origin feature/live-console-v14-foundation
npm ci
node --check server.js
node --check public/app.js
node --check public/v22.js
npm test
$env:HOST = "127.0.0.1"
$env:PORT = "8766"
$env:EVENTFLOW_DATA = "D:\EventFlow-V14-Data"
node server.js
```

Check `/api/health` returns `1.5.2-beta`. In the browser, refresh once with `Ctrl+Shift+R` to load updated versioned assets.

### Manual acceptance checklist

- [ ] Login over Funnel; immediately see event selector without full event payload.
- [ ] Select a test event; navigate through modules without losing selected event.
- [ ] Login as a second account on a separate browser profile or device; both remain logged in.
- [ ] Restart only during a maintenance window and verify both sessions survive.
- [ ] Perform a relevant Live Control action from one operator; the second operator on the same event receives a warning and fresh status.
- [ ] Change another event; the first operator should not see a warning.
- [ ] Admin Event Management shows active and archived events.
- [ ] Archive a synthetic test event; viewer cannot open it and the live event is protected.
- [ ] Restore the same synthetic event; stable P/A IDs and data remain.
- [ ] Use complete ZIP backup before testing permanent deletion; verify the deleted event is absent from all lists.
- [ ] Verify normal media playback, PDF, Excel import and downloads after updating.

## 6. SQLite proposal — requires user approval

**Current state:** EventFlow uses `data.json`; each production write invokes `JSON.stringify(db, null, 2)` plus a synchronous whole-file replacement. This is simple but may become inefficient as records/history grow.

**Recommended future state:** A local SQLite database `EVENTFLOW_DATA/eventflow.sqlite` with schema tables for events, programs, awards, participant rosters, users and audit history, and indexes on event ID / order / status. Keep uploaded media as files under `EVENTFLOW_DATA/media` and keep event catalogs as JSON columns where useful. Use SQLite transactions and WAL for concurrent reads and a single writer.

**Migration safety gates:**
1. Keep the production JSON runtime and live process unchanged until separate consent.
2. Define schema and unit tests in a new isolated branch; verify Windows and Docker driver compatibility.
3. Write a read-only JSON-to-SQLite importer into a *new path*, preserving every UUID, P####, A#### and participant readiness record.
4. Verify counts, checksums, media references, voucher/codes, revision data and authentication.
5. Run a full restore rehearsal and performance comparison using copied test data.
6. Use a reversible configuration flag for cutover and keep an untouched JSON backup for rollback.
7. Never write the active production JSON and SQLite databases simultaneously unless an explicitly tested migration transaction/replay contract exists.

**SQLite is not expected to fix Tailscale Funnel's bandwidth limits or the first internet round trip.** It is primarily for scalable persistence, indexed event-level querying, and better write behavior.
